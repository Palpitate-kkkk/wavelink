# 冻结接收机的完整耗时与增量周期基线

本轮回答一个尚未验证的问题：创新触发和延迟复核减少了模型重建，是否也减少了实际接收耗时？**在本机、本次固定工作负载中，没有。** 不能用重建次数直接替代总体复杂度或耗时结论。

接收策略仍为 v0.15 的冻结实现，创新阈值 2、统计阈值 0.75、共享冷却 32 帧、复核等待 64 帧均不改变。新增 `CachedPeriodicLMMSE` 仅把原周期基线改为缓存逐帧充分统计，不改变其 64 帧拟合窗口、每 32 帧更新时刻和功率/噪声下限。历史报告、算法和保留测试数据不改写。

## 增量计算为什么等价

设每帧导频商为 Z，符号数为 T。固定部分 DFT 设计矩阵的伪逆 A，只需保存每帧的 `|A mean(Z)|²` 及不重叠相邻符号对之差的平均功率除以 2。滑窗中两者的均值，分别对应原批量拟合里的抽头二阶矩与噪声方差。更新时同样扣除 `N0/T * diag(A Aᴴ)`，最后应用相同的数值下限。

这里抽头设计和每帧符号数固定，噪声与路径在一帧内静态。奇数符号时，两种实现均忽略最后一个符号的噪声差分，但均使用全部符号估计信道均值。没有使用真实 PDP、真实噪声或变化时刻。

由于浮点加法顺序不同，只主张数值精度内等价。24 段完整工作负载共 **7,680 帧**的信道估计、拟合统计和有效更新时刻通过 `rtol=atol=1e-10` 检查；最大绝对估计差为 **9.3241e-14**。所有计时重放还要求增量周期与原周期的解调比特、误码数、更新次数及事件序列哈希一致。单元测试额外检查 2,000 帧滑窗累积、短窗口、稀疏导频、奇数符号、零观测下限、冻结模式和 API 时序。

## 测量协议

- 沿用 28 导频、24 数据子载波、FFT=64、CP=16、L=17、QPSK；64 帧初始校准，每个计分帧 20 个符号，共 320 帧。接收端只使用导频，当前帧估计后才摄入观测，新模型最早在下一帧使用，最后一帧不执行无用重建。
- 选择 stationary、weak15、repeat24 三种预设工作负载；初始 Eb/N0 为 6、18 dB，能量定义沿用 [复核协议](followup.md)。新种子 221001..221004，分别固定变化相位 0、8、16、24。仅四种相位，不能声称覆盖全部 32 相位。
- 每段工作负载提前生成共同输入并设为只读；保存输入 SHA-256。波形、信道、噪声生成不进入计时。比较原周期、增量周期、原创新与延迟复核四个接收机。
- 每种方法先完整预热一次；每个工作负载再运行两轮随机 Latin 轮换，共 8 次技术重放，每种方法在每个顺序位置出现两次。共 **768 次计时重放**，96 次预热不计入结果。输出哈希和更新事件必须与预热一致。
- 使用外层 `perf_counter_ns`，分别包围完整构造函数与完整在线循环。在线循环包含信道估计、ZF、QPSK 解调、历史摄入、缓存特征、监测、矩阵求解、原有内部计时器、分配以及输出/事件列表收集；误码评分、哈希、断言、文件写入在计时外。没有把内部计数器相加当作完整耗时。
- 测量期间关闭 Python 自动 GC，结束或异常时恢复原状态。显式设置四个常见 BLAS/OpenMP 线程环境变量为 1，并保存 NumPy 的 Accelerate 构建信息。环境变量不是实测线程数，不声称已验证原生库实际线程数或操作系统调度。
- 每个种子先取 8 次重放的中位数，再对四个种子分支计算均值和描述性 SE。8 次相同输入重放不是 8 个独立信道，三种场景也共享潜在随机流。SE 包含种子、固定相位与计时波动，不是跨机器置信区间。

本轮先完成冒烟运行和测试，再单独执行归档测量；归档测量期间没有并行运行本项目的测试或其他实验。未隔离操作系统后台负载、CPU 频率和温度，因此结果仍是本机单会话基准。

## 本机结果

环境为 Python 3.13.5、NumPy 2.4.1、macOS 26.5.1 arm64，NumPy 使用 Accelerate。表中为完整 **320 帧在线循环**的毫秒数；每项先取重放中位数，再取四个种子均值，不是单帧尾延迟。

| 场景 | 初始 Eb/N0 | 原周期 ms | 增量周期 ms | 原创新 ms | 延迟复核 ms | 复核/增量周期 |
|---|---:|---:|---:|---:|---:|---:|
| stationary | 6 dB | 16.832 | 18.457 | 19.823 | 19.961 | 1.082 |
| stationary | 18 dB | 16.657 | 17.852 | 19.381 | 19.345 | 1.084 |
| weak15 | 6 dB | 17.019 | 18.184 | 20.060 | 20.106 | 1.106 |
| weak15 | 18 dB | 17.077 | 18.006 | 19.787 | 19.943 | 1.108 |
| repeat24 | 6 dB | 17.068 | 18.063 | 20.281 | 20.487 | 1.134 |
| repeat24 | 18 dB | 16.570 | 17.738 | 19.970 | 20.111 | 1.134 |

最后一列先在各个种子上计算复核/增量周期的在线时间比，再取均值，因此不必严格等于表中两列均值相除。完整 SE、初始化和构造加在线总耗时见 [summary.csv](../reports/runtime/summary.csv)，技术重放原始值见 [runs.csv](../reports/runtime/runs.csv)。各阶段分别取中位数，表中初始化中位数加在线中位数不必等于总耗时中位数。

所有单元的周期方法都重建 9 次；复核方法均值仅为 0..5.75 次，但完整在线时间仍高约 **8.2%..13.4%**。原周期反而是本次四种实现中最快的；缓存充分统计需要逐帧额外计算，而原周期每 32 帧才用 NumPy 的批量运算扫描小窗口。本结果表明这份 Python 实现在此尺寸下缓存维护的开销未被节省的重建抵消；未做逐函数剖析，不能把全部差异严格归因于某一个算子。

误码数仅作为重放正确性检查和该工作负载的描述性结果，窗口为完整 320 帧，包含变化前样本，不能与 v0.15 的 post_all 表直接混用。四个种子没有替代 [v0.15 的独立性能测试](followup.md)，本轮没有按计时或误码结果重新选择阈值。

这是冻结算法的工程实现审计，不是无线硬件实测、硬实时验收或跨平台加速结论。测量不包含 RF 前端、帧同步、波形 FFT、真实信道获取和报告评分；初始化单独计时但没有包含输入校准观测的采集成本。后续若声称低复杂度，应进一步优化在线特征与监测、做算子剖析并在其他硬件和帧长复测，同时保留精度/延迟代价。
